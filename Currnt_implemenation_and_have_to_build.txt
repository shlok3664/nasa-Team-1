# 1. Project Overview

## 1.1 What is Earth Twin Engine?

Earth Twin Engine (ETE) is a modular Earth science data exploration, analysis, and trend-detection platform developed for the NASA Space Apps Challenge.

The primary objective is to help users explore environmental datasets, identify long-term patterns, compare geographical regions, perform statistical tests, and understand significant changes in Earth's environmental systems.

The project is designed around the idea that environmental datasets should not be analyzed independently. Instead, different Earth science variables and geographical regions should be brought together through a unified analytical platform.

For example, a user should eventually be able to:

- Explore environmental variables such as rainfall, temperature, humidity, vegetation, and other Earth science indicators.
- Discover available datasets and their sources.
- Select geographical regions for analysis.
- Retrieve and validate environmental observations.
- Normalize measurements into compatible units.
- Organize observations into time series.
- Identify increasing or decreasing trends.
- Determine whether observed trends are statistically significant.
- Compare environmental trends across multiple geographical regions.
- Visualize results using scientific charts and geographical maps.
- Generate understandable scientific interpretations of the results.

ETE is intended to be more than a dashboard. It is a reusable analytical engine that can support different Earth science datasets and scientific analysis workflows.

## 1.2 Main objectives

The project follows these objectives:

1. **Unified environmental data management:** Provide a common structure for environmental variables, datasets, geographical regions, and time-series observations.

2. **Modular scientific architecture:** Keep individual responsibilities separate so that modules can be developed, tested, and extended independently.

3. **Scientific reliability:** Use established statistical techniques instead of relying on visual patterns alone.

4. **Regional comparison:** Enable users to investigate how environmental trends differ between geographical regions.

5. **Explainability:** Present analysis results with appropriate scientific context, assumptions, limitations, and uncertainty.

6. **Extensibility:** Make it possible to add new environmental variables, data providers, statistical methods, and visualization capabilities without restructuring the entire application.

# 3. Architecture Overview

ETE follows a layered, modular architecture.

The central idea is to separate scientific data structures, application workflows, scientific analysis, and presentation.

The application should not depend directly on the frontend framework or on a particular scientific data provider.

## 3.1 High-level architecture

```text
                    FRONTEND
              React + TypeScript
                       |
                       |
              Visualization API
                       |
                       |
              APPLICATION LAYER
                       |
     +-----------------+------------------+
     |                 |                  |
 Data Management   Scientific Analysis   Presentation
     |                 |                  |
     |                 |                  |
 Variable          Trend Analysis       Visualization
 Discovery         Statistical Testing  Scientific
 Data Sources      Regional Comparison   Interpretation
 Regions
 Acquisition
 Validation
 Normalization
 Time Series
     |                 |                  |
     +-----------------+------------------+
                       |
                 DOMAIN LAYER
                       |
       Earth Variables / Time Series
       Spatial Regions / Observations
       Temporal Resolutions / Metadata
                       |
                       |
               EXTERNAL DATA SOURCES
                       |
       Satellite / Climate / Weather /
          Environmental Data Providers
```

This is a conceptual architecture. The actual Python implementation uses application modules, domain objects, services, handlers, commands, queries, and events.

## 3.2 Application Core

The Application Core provides the infrastructure used by the rest of the application.

Its responsibilities include:

- Application lifecycle management.
- Module registration and dependency management.
- Service registration and resolution.
- Event publication and subscription.
- Command dispatching.
- Query dispatching.
- Configuration management.
- Logging.
- Error handling.
- Resource management.

This means scientific modules do not need to independently implement infrastructure such as event handling or application lifecycle management.

## 3.3 Module communication

The application uses three important communication mechanisms.

**Commands:** Represent requests to perform operations that may change application state or initiate work.

**Queries:** Represent requests to retrieve information without performing a state-changing operation.

**Events:** Represent things that have already happened.

For example:

```text
AcquireDatasetCommand
          |
          v
DataAcquisitionHandler
          |
          v
DatasetAcquiredEvent
          |
          v
Other interested modules
```

The event dispatcher supports subscriptions, publication, and dispatch-result reporting.

Application events contain:

- Event ID
- Occurrence timestamp
- Optional correlation ID

Correlation IDs help trace related operations across modules.

## Module 21 — Statistical Testing

Package:

`application/modules/statistical_testing/`

Purpose:

Provide a reusable statistical testing system for environmental analysis.

Three statistical methods have been implemented:

### 1. Mann–Kendall Test

A non-parametric test used to evaluate whether a time series exhibits a statistically significant monotonic trend.

The implementation includes:

- Tie-corrected variance.
- Continuity correction.
- Asymptotic normal p-value calculation.

### 2. One-Sample T-Test

Tests whether the mean of one sample differs significantly from a specified reference value.

Includes:

- Test statistic.
- P-value.
- Degrees of freedom.
- Confidence interval for the mean difference.

### 3. Welch's T-Test

Compares the means of two independent samples without assuming equal population variances.

Includes:

- Welch test statistic.
- Degrees of freedom.
- P-value.
- Confidence interval for the mean difference.

The module also implements numerical routines for:

- Regularized incomplete beta function.
- Student's t-distribution CDF.
- Student's t quantile using bisection.

The module does not require SciPy.

Statistical results preserve:

- Test method.
- Input series IDs.
- Test statistic.
- P-value.
- Significance level.
- Significance decision.
- Estimated effect.
- Degrees of freedom.
- Sample sizes.
- Valid and missing observation counts.
- Confidence intervals.
- Assumptions.
- Warnings.
- Analysis timestamp.

The statistical testing service uses a registry of test strategies, making it possible to add additional methods later.

## Module 22 — Regional Comparison

Package:

`application/modules/regional_comparison/`

Purpose:

Compare environmental trends across multiple geographical regions.

This module builds on:

- Region Manager.
- Time-Series Management.
- Trend Analysis.

Implemented components:

- RegionalTrendResult.
- RegionalComparisonResult.
- RegionalComparisonService.
- CompareRegionsCommand.
- RegionalComparisonCompletedEvent.
- RegionalComparisonFailedEvent.
- RegionalComparisonModule.

The comparison workflow:

1. Receives a variable and geographical region selection.
2. Retrieves registered time series for the variable.
3. Determines which series belong to the selected regions.
4. Analyzes each series independently.
5. Aggregates the results for each region.
6. Calculates regional summary metrics.
7. Ranks regions based on the absolute mean Sen's slope.

Regional summaries include:

- Mean linear slope.
- Mean Sen's slope.
- Mean Kendall tau.
- Trend direction.
- Increasing, decreasing, stable, and insufficient-data counts.
- Number of statistically significant trends.
- Total observation counts.
- Valid observation counts.
- Missing observation counts.

The comparison service supports overlapping geographical boundaries.

The ranking uses the absolute mean Sen's slope, which measures the magnitude of change. It should not be interpreted as a ranking of environmental severity without additional variable-specific context.

# 7. Domain Layer

The domain layer provides the core scientific objects used by the application modules.

Important domain entities and value objects include:

## EarthVariable

Represents an environmental variable.

Contains:

- Variable ID.
- Name.
- Description.
- Variable category.
- Variable metadata.

## VariableMetadata

Contains:

- Unit.
- Supported temporal resolutions.
- Spatial resolution in metres.
- Temporal coverage.
- Keywords.
- Supported data source IDs.

## VariableCategory

The supported categories include:

- ATMOSPHERE
- OCEAN
- LAND
- HYDROLOGY
- CRYOSPHERE
- BIOSPHERE
- OTHER

## GeographicRegion

Represents a named geographical region.

Contains:

- Region ID.
- Name.
- Spatial boundary.
- Description.

## SpatialBoundary

Represents the geographical extent of a region using:

- South latitude.
- North latitude.
- West longitude.
- East longitude.

Supports geographical containment and antimeridian-aware boundaries.

## SpatialCoordinate

Represents a geographical coordinate using latitude and longitude.

## TimeSeries

Represents observations of a particular environmental variable at a particular location.

Contains:

- Series ID.
- Environmental variable.
- Geographical location.
- Temporal resolution.
- Observation points.
- Optional aggregation metadata.

Provides properties for:

- Total observation count.
- Valid observation count.
- Missing observation count.
- Start timestamp.
- End timestamp.

## TimeSeriesPoint

Represents an individual observation:

- Timestamp.
- Value.

The value can be `None` to represent missing data.

This is important because missing environmental observations must not be confused with actual zero measurements.

## Module 24 — Scientific Interpretation

**Status: Not yet implemented.**

Package:

`application/modules/scientific_interpretation/`

### Purpose

Translate scientific analysis results into understandable explanations while preserving scientific accuracy.

The module should help users understand what the analytical results mean, rather than simply displaying numerical values.

For example:

Instead of displaying only:

```text
Trend direction: INCREASING
Sen's slope: 0.025
P-value: 0.003
```

The system should be able to generate an explanation such as:

```text
The analyzed variable exhibits an increasing trend over
the selected observation period.

The estimated Sen's slope is positive, indicating an
average increase over time.

The statistical test indicates that the observed trend
is statistically significant at the selected significance
level.
```

The exact interpretation must depend on the variable's unit, temporal resolution, trend result, and statistical evidence.

### Expected functionality

**Trend Interpretation**

- Explain increasing trends.
- Explain decreasing trends.
- Explain stable results.
- Explain insufficient-data results.
- Describe trend magnitude in the appropriate units.
- Explain statistical significance.

**Statistical Interpretation**

- Explain p-values.
- Explain significance levels.
- Explain confidence intervals.
- Explain sample sizes and missing observations.
- Describe test assumptions and warnings.

**Regional Interpretation**

- Compare regional trend directions.
- Identify differences in trend magnitudes.
- Highlight regions with statistically significant trends.
- Explain uncertainty in regional summaries.

**Scientific Limitations**

The interpretation system must not:

- Claim causation from correlation.
- Treat statistical significance as practical importance.
- Invent missing data.
- Overstate confidence.
- Treat insufficient data as evidence of no change.
- Ignore assumptions and methodological limitations.

### Possible output structure

A scientific interpretation could include:

- Summary.
- Observed pattern.
- Trend magnitude.
- Statistical evidence.
- Regional comparison.
- Confidence and uncertainty.
- Data limitations.
- Methodological notes.

### Integration

The module should reuse existing outputs from:

- Trend Analysis.
- Statistical Testing.
- Regional Comparison.
- Domain metadata.

It must not reimplement those scientific algorithms.

The module should publish interpretation-completion and failure events using the existing application event infrastructure.

### Important design consideration

Scientific interpretation should be explainable and traceable.

Every claim should be grounded in an actual analytical result, measurement, or metadata field.

If an interpretation cannot be supported by the available data, the system should explicitly state that limitation.

# 12. Data Integration and External Providers

Although the data-management architecture is implemented, the complete production data-provider ecosystem is not yet established.

The DataSourceAdapter protocol and DataSourceManager provide the foundation for integrating providers.

Potential future integrations include:

- NASA Earth observation datasets.

- Other relevant environmental data providers.

Provider integration should be performed through individual adapters.

Each adapter should:

1. Identify the variables it supports.
2. Check whether it is available.
3. Validate the incoming request.
4. Retrieve the requested dataset.
5. Convert the provider response into ETE domain objects.
6. Preserve source metadata and provenance.
7. Handle API errors, timeouts, and missing data.

The team should prioritize a small number of reliable, usable data sources rather than integrating many providers superficially.

Actual provider availability, authentication requirements, spatial coverage, temporal coverage, and licensing should be verified before implementation.

# 13. Important Architectural Decisions

These decisions should be preserved while continuing development.

## 13.1 Keep the backend modular

Avoid placing all functionality into one large service or application class.

Each module should have a clearly defined responsibility.

## 13.2 Keep scientific calculations separate from visualization

Visualization should prepare presentation-ready data, not repeat scientific calculations.

Trend Analysis and Statistical Testing remain responsible for their respective algorithms.

## 13.3 Preserve missing observations

Missing observations are represented by `None`.

Do not replace missing values with zero unless an explicit scientific preprocessing operation justifies it.

## 13.4 Preserve provenance

Data should retain information about its source and transformations.

This is essential for reproducibility and scientific trust.

## 13.5 Avoid unsupported statistical claims

A positive or negative slope alone does not establish a statistically significant trend.

A significant statistical result does not establish causation.

## 13.6 Use the existing application infrastructure

New modules should reuse:

- ApplicationModule.
- ApplicationContext.
- ServiceRegistry.
- EventDispatcher.
- CommandDispatcher.
- QueryDispatcher.
- Existing domain models.

Do not independently recreate these systems.

## 13.7 Maintain testability

Every new module should have dedicated tests covering:

- Normal operation.
- Invalid inputs.
- Missing dependencies.
- Failure handling.
- Lifecycle behaviour.
- Event integration.
- Edge cases.

## 13.8 Keep dependencies minimal

Avoid adding large libraries unless they provide a genuine requirement.

The existing Python foundation should remain lightweight and portable.
